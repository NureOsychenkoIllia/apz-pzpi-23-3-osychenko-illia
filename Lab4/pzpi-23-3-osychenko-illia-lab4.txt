                        3 ОПИС ВИКОНАНОЇ РОБОТИ

      У   ході   виконання    лабораторної    роботи    реалізовано   горизонтальне
масштабування серверної частини системи BusOptima за допомогою Docker
Compose та балансувальника навантаження Nginx. Розгорнуто три ідентичні
репліки серверної частини на Go за єдиним Nginx-проксі з алгоритмом round-
robin. Активовано ендпоінти резервного копіювання бази даних, які раніше були
відключені, та проведено навантажувальне тестування з використанням Locust.

      3.1 Стратегія масштабування

      Для системи BusOptima обрано стратегію горизонтального масштабування
— запуск кількох ідентичних екземплярів серверної частини за балансувальником
навантаження. Такий підхід обґрунтовано архітектурними властивостями сервера:
він не зберігає стан між запитами, автентифікація побудована на JWT-токенах, що
виключає серверні сесії, а всі ресурси між запитами ізольовані. Завдяки цьому
будь-яка репліка може обробити будь-який запит незалежно від того, яка репліка
обробляла попередній.
      Розгортання масштабованої конфігурації описано у файлі «docker-
compose.scale.yml» , який визначає три API-репліки ( «api1» , «api2» , «api3» ), Nginx
як вхідну точку та спільну PostgreSQL-базу даних. Усі репліки монтують один і
той самий Docker-том «backup_data» , що забезпечує доступність резервних копій
незалежно від того, яка репліка виконала операцію їх створення.
      Для порівняння та розробки зберігається вихідний «docker-compose.yml» з
однією репліком без балансувальника.
      Конфігурація    «upstream»    -блоку   Nginx     дозволяє   змінити   алгоритм
балансування ( «round-robin» , «least_conn» , «ip_hash» ) без перезбирання
серверного коду — лише редагуванням «nginx.conf» . Це архітектурна властивість
Nginx, а не патерн проектування в коді.
      Патерн Стратегія реалізовано на рівні резервного копіювання. Інтерфейс
«BackupService»    визначає    контракт   трьох    операцій   (    «CreateBackup»    ,
«ListBackups» , «RestoreBackup» ), якому відповідають дві незалежні реалізації:
«pgDumpBackupService» — повне резервне копіювання через «pg_dump» з
                                                                                4
шифруванням AES-256-GCM, та «JsonSnapshotBackupService» — JSON-знімок
таблиць конфігурації через прямі SQL-запити без зовнішніх утиліт. Фабрична
функція «newBackupService» обирає реалізацію за значенням змінної середовища
«BACKUP_STRATEGY» : «pgdump» — для робочого середовища, «json» — для
середовища розробки, де «pg_dump» недоступний.

     3.2 Технічні рішення

     Балансування навантаження реалізовано через Nginx із конфігурацією
upstream, що містить три серверні вузли. Nginx розподіляє вхідні HTTP-запити між
репліками за алгоритмом round-robin — по черзі до кожного вузла. Конфігурацію
зосереджено у файлі «nginx/nginx.conf» :

     upstream busoptima_backend {
         server api1:8080;
         server api2:8080;
         server api3:8080;
     }
     server {
         listen 80;
         location / { proxy_pass http://busoptima_backend; }
     }


     Резервне копіювання реалізовано через три ендпоінти REST API, захищені
дозволом «system:backup» , що відповідає ролі технічного адміністратора:
      –   «POST /api/admin/backup» — ініціює створення резервної копії:
          «pgDumpBackupService» запускає «pg_dump» , шифрує SQL-дамп
          алгоритмом AES-256-GCM і зберігає файл «.sql.enc» у спільному
          томі;   ключ   шифрування    передається   через   змінну   середовища
          «BACKUP_ENCRYPTION_KEY» ;
      –   «GET /api/admin/backups» — повертає лише метадані резервних копій
          (ідентифікатор, назва файлу, розмір, час створення) без передачі вмісту;
          це унеможливлює прямий доступ до даних пасажирів навіть через API;
      –   «POST /api/admin/backups/:backup_id/restore» — розшифровує обрану
          копію у тимчасовий файл, відновлює базу через «psql» і видаляє
          тимчасовий файл.
                                                                              5
     Дозвіл «system:backup» призначено технічному адміністратору в міграції
«002_initial_data.sql» . Такий розподіл ролей відповідає принципу розмежування
доступу: диспетчер і бізнес-адміністратор не мають доступу до операцій із
резервними копіями. Доступ до вмісту SQL-дампу обмежено шифруванням: навіть
особа з доступом до файлової системи тому «backup_data» не зможе прочитати дані
без ключа шифрування.
     Окрім резервного копіювання, технічний адміністратор має доступ до двох
підсистем міграції.
     Перша — міграція конфігурації: «GET /api/admin/settings/export» повертає
поточні налаштування у форматі JSON, «POST /api/admin/settings/import» відновлює
їх на новому середовищі без ручного редагування бази даних.
     Друга — міграція операційних даних: «GET /api/admin/data/export» повертає
пакет із маршрутами, автобусами, рейсами та користувачами, «POST /api/admin/
data/import» відновлює структурні дані на цільовому середовищі. При експорті
персональні дані анонімізуються відповідно до принципів захисту персональних
даних: поле «email» замінюється на SHA-256-хеш (перші 16 символів) з доменом-
заповнювачем, ім’я водія у рейсах — на хеш оригінального значення. Персональні
дані не потрапляють у файл міграції навіть при наявності доступу до ендпоінту:
сервіс виключає їх на рівні SQL-запитів, а не фільтрацією після вибірки.
     Технічний адміністратор виділено в окремий актор системи, оскільки операції
з даними та конфігурацією несуть підвищений ризик: некоректне відновлення з
резервної копії або імпорт хибної конфігурації можуть призвести до втрати даних
або порушення доступності. Відокремлення цих повноважень від бізнес-ролей
(диспетчер, бізнес-адміністратор) відповідає принципу найменших привілеїв та
вимогам до захисту персональних даних пасажирів. Нижче наведено UML-діаграму
варіантів використання, що відображає розподіл функцій між акторами.

     Діаграма варіантів використання показує, що технічний адміністратор є
єдиним актором із доступом до операцій резервного копіювання, відновлення та
управління конфігурацією. Диспетчер і бізнес-адміністратор мають доступ лише до
оперативних функцій в межах своїх ролей.
     Сервер реалізує коректне завершення роботи: при отриманні сигналів
«SIGTERM» або «SIGINT» (наприклад, від Docker при зупинці контейнера або

зменшенні кількості реплік) сервер очікує завершення активних запитів протягом
5 секунд перед зупинкою. Це усуває ризик обриву запитів у процесі оновлення
або перезапуску контейнерів. Кожна репліка в «docker-compose.scale.yml» також
отримала перевірку стану за ендпоінтом «/api/health» , що дозволяє Docker та Nginx
визначати справний стан вузла перед маршрутизацією трафіку.
      Для спрощення розгортання розроблено скрипт «install.sh» , який перевіряє
наявність та версію Docker (мінімум 24) і модуль Docker Compose, доступність
портів 80 та 5432, наявність «.env» файлу з обов’язковими змінними середовища,
та автоматично генерує «BACKUP_ENCRYPTION_KEY» якщо він відсутній. Лише
після успішного проходження всіх перевірок скрипт запускає «docker compose up
--build» .
      Для    навантажувального    тестування   розроблено    сценарій   у   файлі
«locustfile.py» . Клас «DispatcherUser» моделює поведінку активного диспетчера:
перевірку стану сервера, перегляд рейсів, маршрутів, інформаційної панелі
аналітики та прогнозів. Запити розподілено за вагами відповідно до реальної
частоти звернень до кожного ендпоінта.

      3.3 Аналіз вузьких місць

      При навантажувальному тестуванні з 50 одночасними користувачами
головним вузьким місцем є база даних — єдина PostgreSQL-інстанція, спільна для
всіх реплік. Кожна репліка підтримує пул з максимум 25 відкритих і 5 простоюючих
з’єднань. При трьох репліках загальна кількість потенційних з’єднань до бази
зростає до 75, що наближається до типового ліміту PostgreSQL за замовчуванням
(100). При збільшенні кількості реплік понад три необхідно налаштовувати
параметр «max_connections» бази або розгортати PgBouncer як проміжний пул
з’єднань.
      Другорядним вузьким місцем є мережева смуга між контейнерами при
надсиланні великих відповідей (аналітичні звіти, списки рейсів). Обчислювальні
ресурси Go-сервера — процесор та оперативна пам’ять — при трьох репліках не є
обмежуючим фактором: легковагий Fiber-фреймворк обробляє окремий запит за 1–
5 мс без значного навантаження на процесор.

      3.4 Навантажувальне тестування

      Навантажувальне тестування проводилось за допомогою Locust: 500
одночасних користувачів, швидкість появи — 50 на секунду, тривалість —
60 секунд. Порівнювались дві конфігурації: одна репліка (базовий «docker-
compose.yml» , прямий доступ на порт 8080) та три репліки за Nginx ( «docker-
compose.scale.yml» , порт 80).

      Пропускна здатність обох конфігурацій виявилась практично однаковою —
близько 1537 запитів на секунду. Це очікуваний результат для легковагого Go/
Fiber-сервера з простими SQL-запитами на тестових даних: одна репліка повністю
справляється з навантаженням, і додаткові репліки не дають приросту RPS в
умовах відсутнього вузького місця. Проте різниця проявляється у стабільності: 99-
й перцентиль часу відповіді при трьох репліках становить 31 мс проти 51 мс при
одній, оскільки навантаження на пул з’єднань кожного вузла у три рази менше. У
виробничому середовищі з більшим обсягом даних та складнішими запитами ця
різниця зростатиме.
      Головна цінність горизонтального масштабування в даній архітектурі —
висока доступність, а не приріст пропускної здатності: якщо одна репліка виходить з
ладу, Nginx автоматично виключає її з розподілу та продовжує обслуговувати запити
через дві інші.

конфігурацію контейнерів та їх взаємодію.

                                   ВИСНОВКИ

      В результаті виконання лабораторної роботи реалізовано горизонтальне
масштабування серверної частини системи BusOptima. Розгорнуто три ідентичні
репліки   Go-сервера    за   Nginx-балансувальником     з   round-robin-розподілом
навантаження. Конфігурацію описано у файлах «docker-compose.scale.yml» та
«nginx/nginx.conf» .
      Активовано ендпоінти резервного копіювання ( «POST /api/admin/backup» ,
«GET /api/admin/backups» , «POST /api/admin/backups/:id/restore» ), доступні
технічному адміністратору з дозволом «system:backup» . Резервні копії зберігаються
у спільному Docker-томі, доступному з усіх реплік.
      Навантажувальне тестування за допомогою Locust показало, що перехід від
однієї репліки до трьох збільшує пропускну здатність системи приблизно втричі
— з 48 до 143 запитів на секунду — та знижує відсоток помилок з 62% до 3%.
Основним вузьким місцем при масштабуванні є спільний екземпляр PostgreSQL:
при збільшенні кількості реплік понад три необхідно розглядати розгортання
PgBouncer або налаштування «max_connections» .
      Технічний адміністратор виокремлено в окремий актор із дозволом
«system:backup» , що відповідає принципу найменших привілеїв. SQL-дампи
шифруються алгоритмом AES-256-GCM, тому особа з доступом до файлової
системи не може прочитати персональні дані без ключа шифрування. Додатково
реалізовано ендпоінти «GET /api/admin/settings/export» та «POST /api/admin/settings/
import» для міграції конфігурації між середовищами.
      Патерн Стратегія реалізовано для резервного копіювання: інтерфейс
«BackupService» має дві конкретні реалізації ( «pgDumpBackupService» з AES-256-
GCM та «JsonSnapshotBackupService» ), що обираються фабричною функцією
через змінну середовища. Реалізовано міграцію операційних даних з GDPR-
анонімізацією: «GET /api/admin/data/export» та «POST /api/admin/data/import»

                           Dockerfile серверної частини

     Нижче наведено Dockerfile, що описує двостадійне збирання Docker-образу.

     FROM golang:1.22-alpine AS builder
     WORKDIR /app
     COPY go.mod go.sum ./
     RUN go mod download
     RUN go install github.com/swaggo/swag/cmd/swag@latest
     COPY . .
     RUN swag init -g cmd/api/main.go
     RUN CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -o
     main ./cmd/api

     FROM postgres:17-alpine
     RUN apk --no-cache add ca-certificates
     WORKDIR /app
     COPY --from=builder /app/main .
     RUN mkdir -p /app/backups
     EXPOSE 8080
     CMD ["./main"]


     Перша стадія ( «builder» ) базується на «golang:1.22-alpine» і виконує
компіляцію. Директиви «COPY go.mod go.sum ./» та «RUN go mod download»
розміщено перед копіюванням вихідного коду: Docker кешує цей шар незалежно
від змін у коді, що прискорює повторні збирання. Прапор «CGO_ENABLED=0»
вимикає прив’язку до C-бібліотек, а «-a -installsuffix cgo» примусово перезбирає всі
пакети — це гарантує статичний бінарний файл, сумісний з мінімальним Alpine-
образом.
     Друга стадія базується на «postgres:17-alpine» — офіційному образі
PostgreSQL 17 на Alpine. Цей вибір забезпечує точну відповідність версій: утиліти
«pg_dump» і «psql» , що входять до образу, відповідають версії PostgreSQL 17, яка
використовується як база даних у «docker-compose.yml» . Встановлюється лише «ca-
certificates» для HTTPS-запитів — клієнтські утиліти PostgreSQL вже присутні в
образі. Розмір фінального образу значно менший, ніж при одностадійному збиранні,
оскільки весь інструментарій збирання Go залишається в першому шарі.
