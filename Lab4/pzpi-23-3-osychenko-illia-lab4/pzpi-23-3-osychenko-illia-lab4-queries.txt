=== Запит 1: Конфігурація горизонтального масштабування

Назва інструменту та версія: Claude Code (claude-sonnet-4-6)

Мета використання: Розробка Docker Compose конфігурації для запуску трьох ідентичних реплік Go-сервера BusOptima за балансувальником навантаження Nginx.

Внесок автора: Автор самостійно визначив кількість реплік, вимогу до спільного тому для резервних копій та структуру мережі на основі архітектури існуючого сервера. Перевірив відповідність конфігурації реальним іменам сервісів та змінним середовища проєкту.

Початковий запит:

«Розроби docker-compose.scale.yml для горизонтального масштабування Go-сервера BusOptima: три API-репліки (api1, api2, api3), Nginx як балансувальник на порту 80, спільна PostgreSQL з health-check через pg_isready, shared volume backup_data для зберігання SQL-дампів.»

Відповідь: Згенеровано docker-compose.scale.yml із трьома репліками серверної частини на Go, сервісом Nginx, що монтує nginx.conf лише для читання, PostgreSQL з перевіркою стану через pg_isready, іменованими томами postgres_data та backup_data та мережею busoptima_network типу bridge. Кожна репліка залежить від postgres через condition: service_healthy.

Уточнення:

«Як забезпечити, щоб усі три репліки мали доступ до одних і тих самих резервних копій незалежно від того, яка репліка виконала операцію pg_dump?»

Відповідь: Для цього достатньо змонтувати один іменований том backup_data у директорію /app/backups кожної з реплік. Docker гарантує, що всі контейнери, що монтують один і той самий іменований том, бачать ідентичну файлову систему, тому файл, створений репліками api1, буде доступний при запиті через api2 або api3.

=== Запит 2: Конфігурація балансувальника навантаження

Назва інструменту та версія: Claude Code (claude-sonnet-4-6)

Мета використання: Написання nginx.conf для розподілу вхідних HTTP-запитів між трьома репліками сервера за алгоритмом round-robin.

Внесок автора: Автор самостійно визначив імена upstream-вузлів відповідно до імен сервісів у docker-compose.scale.yml та перевірив конфігурацію на коректність заголовків проксі.

Початковий запит:

«Напиши nginx.conf для round-robin балансування між вузлами api1:8080, api2:8080, api3:8080 з передачею заголовків Host, X-Real-IP та X-Forwarded-For, таймаутами proxy_connect_timeout 5s та proxy_read_timeout 60s.»

Відповідь: Згенеровано nginx/nginx.conf з upstream-блоком busoptima_backend, директивою proxy_pass http://busoptima_backend, трьома proxy_set_header та таймаутами з'єднання і читання.

Уточнення:

«Як змінити алгоритм балансування з round-robin на least_conn без зміни серверного коду?»

Відповідь: Достатньо додати директиву least_conn; у тіло upstream-блоку перед переліком серверів. Nginx підтримує зміну алгоритму виключно на рівні конфігурації: round-robin є типовим і не потребує явного оголошення, тоді як least_conn та ip_hash оголошуються однією директивою. Серверний код при цьому не змінюється.

=== Запит 3: Сценарій навантажувального тестування

Назва інструменту та версія: Claude Code (claude-sonnet-4-6)

Мета використання: Розробка locustfile.py для вимірювання пропускної здатності API при різній кількості активних реплік.

Внесок автора: Автор самостійно визначив перелік ендпоінтів для тестування та ваги задач на основі реальної частоти звернень у системі BusOptima. Додав механізм передачі JWT-токена через змінну середовища.

Початковий запит:

«Створи locustfile.py для навантажувального тестування BusOptima API: клас DispatcherUser з задачами health_check (вага 5), get_trips (вага 4), get_routes (вага 3), get_dashboard (вага 2), get_forecast (вага 1). JWT-токен передавати через змінну середовища BUSOPTIMA_TOKEN або аргумент --token командного рядка.»

Відповідь: Згенеровано locustfile.py з класом DispatcherUser, wait_time between(0.1, 0.5), п'ятьма задачами з вагами, обробником init_command_line_parser для аргументу --token та заголовком Authorization: Bearer у кожному запиті.

Уточнення:

«Як порівняти продуктивність однієї репліки і трьох реплік за допомогою одного сценарію?»

Відповідь: Достатньо запускати той самий locustfile двічі, змінюючи лише параметр --host: для однієї репліки вказати http://localhost:8080 (прямий доступ), для трьох — http://localhost:80 (через Nginx). Результати Locust (RPS, середній час відповіді, відсоток помилок) автоматично агрегуються у веб-інтерфейсі та CSV-звіті.

=== Запит 4: UML-діаграми для звіту

Назва інструменту та версія: Claude Code (claude-sonnet-4-6)

Мета використання: Генерація Mermaid-діаграм для UML-нотацій розгортання, компонентів, діяльності та варіантів використання.

Внесок автора: Автор самостійно визначив склад акторів, набір компонентів та послідовність дій у сценарії резервного копіювання та відновлення на основі реального коду серверної частини. Перевірив діаграми на відповідність фактичній архітектурі після конвертації у PNG.

Початковий запит:

«Згенеруй чотири Mermaid-діаграми: deployment — Client → Nginx → api1/api2/api3 → PostgreSQL + backup volume; component — Nginx, три API-репліки з BackupHandler; activity-backup — адмін → POST /backup → pg_dump → список → POST /restore → psql; use-case — актори Диспетчер, Бізнес-адміністратор, Технічний адміністратор (system:backup), Водій.»

Відповідь: Згенеровано чотири .mmd файли у форматі Mermaid у директорії diagrams/. Конвертація до PNG виконується командою mmdc -i diagram.mmd -o diagram.png -w 1200.

Уточнення:

«Як показати на діаграмі варіантів використання, що Технічний адміністратор є окремим актором із вузькими системними повноваженнями, а не розширенням ролі бізнес-адміністратора?»

Відповідь: Технічного адміністратора слід зображувати як окремий елемент actor з підписом, що містить позначку дозволу (system:backup), а стрілки від нього — лише до варіантів використання резервного копіювання, відновлення та управління конфігурацією. Бізнес-адміністратор при цьому не має стрілок до цих юзкейсів, що наочно демонструє розмежування доступу.

=== Запит 5: Написання звіту

Назва інструменту та версія: Claude Code (claude-sonnet-4-6)

Мета використання: Написання академічного звіту у форматі Typst з описом стратегії масштабування, технічних рішень та результатів навантажувального тестування.

Внесок автора: Автор самостійно визначив структуру звіту, числові результати навантажувального тестування та аргументацію вузьких місць на основі реальних параметрів пулу з'єднань PostgreSQL. Перевірив відповідність тексту шаблону попередніх лабораторних робіт.

Початковий запит:

«Напиши звіт лабораторної роботи №4 у форматі Typst: безособові речення, без жирного тексту в основному тексті, мінімум списків. Теми: горизонтальне масштабування через Docker Compose + Nginx round-robin, патерн Стратегія для алгоритму балансування та BackupService, резервне копіювання через pg_dump/psql, окремий актор технічного адміністратора, ендпоінти export/import конфігурації, навантажувальне тестування Locust (50 users, 60s) з порівнянням 1 і 3 реплік.»

Відповідь: Написано повний звіт із секціями Завдання, Опис виконаної роботи та Висновки. У розділі Технічні рішення описано ендпоінти резервного копіювання, ендпоінти експорту та імпорту конфігурації та окремий актор технічного адміністратора. У розділі Стратегія масштабування пояснено застосування патерну Стратегія. Навантажувальне тестування супроводжується таблицею порівняння конфігурацій та чотирма UML-діаграмами.

Уточнення:

«Як академічно обґрунтувати виокремлення технічного адміністратора в окремий актор, не посилаючись лише на технічну реалізацію?»

Відповідь: Виокремлення обґрунтовується принципом найменших привілеїв: кожен актор має доступ лише до тих операцій, які необхідні для виконання його функцій. Операції з резервними копіями та конфігурацією несуть підвищений ризик для цілісності даних і доступності системи, тому їх не можна делегувати оперативним ролям — диспетчеру або бізнес-адміністратору. Крім того, доступ до дампів бази даних означає доступ до персональних даних пасажирів, що вимагає окремого контролю відповідно до вимог захисту персональних даних.
